# 跑步模块设计 · v0.80（方案，不含实现）

> 需求书：[RUN_MODULE_SPEC.md](RUN_MODULE_SPEC.md)。本文只回答「怎么接进现有系统」，不写实现。
> 结论先行：**跑步不走六表契约、不进 CSV 26 列；用 `state.run` 本地账本 + 模板内 `RUN_PLAN` 单源。**
> 落点 **v0.80**，不在 v0.70 挤进来。

## 一页结论

| 问题 | 结论 | 代价 |
|---|---|---|
| 记录形状 | `state.run = {v,hrMax,daily,logs}`；轻松跑存 `durSec/distKm/hrAvg/hrMax`，间歇存 `reps/avgSec/hrAvg/hrRecover` | 跑步记录不进 CSV / JSONL，只在本地账本与整机备份里 |

## 1 · 记录的最小数据形状

现有 `sets × reps × load_kg` 装不下时长 / 距离 / 配速 / 心率 / 体感，这一点没有争议。争议只在「数据放哪」。

### 1.1 选定形状

```js
state.run = {
  v: 1,
  hrMax: 190,
  daily: { B: 'easy', D: 'interval' },     // 哪一天跑什么；只认 B/D
  logs: {
    '3-B': { week:3, day:'B', type:'easy', at:'2026-11-25', done:true,
             durSec:1800, distKm:4.9, hrAvg:132, hrMax:141, note:'' },
    '3-D': { week:3, day:'D', type:'interval', at:'2026-11-28', done:true,
             reps:4, avgSec:76, hrAvg:168, hrRecover:138, note:'' }
  }
}
```

- 键 `week-day`，一周最多一条；`logs` 保留未知字段，不整条重建。
- 派生值全部现算：配速 `durSec/distKm`、间歇总距离 `reps×300m`、工作秒 `reps×avgSec`、跑步机速度 `300/avgSec×3.6`、心率区间 `runZone(hr)`。
- 不存 RPE。轻松跑以心率为权威，300m 间歇以配速为权威（需求书 §1）。

### 1.2 为什么不塞进 `sets × reps × load_kg`

`load_kg` 对跑步没有语义；`sets/reps` 描述的是「组 × 次」，而跑步是「时长 × 距离 × 配速 × 心率 × 恢复」。硬映射会得到三个坏结果：统计口径污染（吨位、e1RM、完成度）、计划交换列语义含混、任何一次列调整都要动冻结协议。

## 2 · 扩六表契约，还是新增并行记录表

### 2.1 方案 A：扩 `Workouts`

给 `Workouts` 加 `run_type / duration_sec / distance_m / pace_sec_km / hr_avg / hr_max / hr_recover` 等列，用第 21–27 列承载跑步行。

代价：

- 动 `schema/RPL-Plan-v1.json` 的 `Workouts.columns` 与 `role_columns`，所有读契约的 Python / gate / 成品三处同步；
- `plan_xlsx.py` 导入导出映射、往返零格差测试全部要扩；
- 为守住 **CSV 26 列协议**，`unifiedRecords()` 必须把跑步行过滤掉，等于「计划里有、日志里没有」，两边口径永久分叉；
- 力量侧所有按 `movement/tier/mode` 分支的代码都要加「这行可能是跑步」的空值防御；
- 一旦列名或列序再动，冻结契约与 `_sabotage` 靶串一起返工。

结论：**v1 不选**。它把「新增一个模块」变成「改冻结协议」，风险与收益不成比例。

### 2.2 方案 B：并行本地账本（选定）

`state.run` 独立于 `weeks[].exercises`，与 `health` / `hpr` 同一类「纯加法本地键」。

收益：

- 六表契约、`seed.json`、`data/*.xlsx`、CSV 26 列、`rxlib.py`、`wkbook.py` 全部不动；
- 跑步卡是独立 UI，不参与力量行的渲染、进阶、e1RM、吨位；
- 记录只在本机，不导出 CSV，不会破坏「CSV 26 列」的对外承诺。

代价：

- 跑步处方暂时不能从 xlsx 编辑（v1 用 `RUN_PLAN` 常量，改处方要发版）；
- 跑步记录不进 CSV / JSONL；整机备份（四分片 / 启动信封）会带走它，但单独的「导出 CSV」不会。

### 2.3 以后要「在计划里编辑跑步」时的升级路径

不改 `Workouts`，**新增第 9 张可选表 `RunPlan`**（契约 v2 的加法扩展）：

- 列：`week / day / type / duration_min / hr_low / hr_high / reps / target_sec / note`；
- 导入时映射到 `state.run.daily` + 派生处方，日志仍在 `state.run.logs`；
- CSV 26 列继续只导力量，跑步计划只走 xlsx/JSON 计划交换；
- 往返测试扩一张表，不碰 `Workouts` 的任何列。

这条路径留到用户明确要「自己改跑步课表」时再做。

## 3 · 计划侧：跑步周怎么排进现有 Workouts

### 3.1 v1：挂在现有日上，不新增行类型

- 需求书指定 **DAY B = 轻松跑，DAY D = 300m 间歇**，都是现有 `Days` 表里已有的日。
- `RUN_PLAN` 是模板内唯一单源，9 周一张表，索引 `week-1`，越界夹到首/末项。
- `Workouts` 不新增行；跑步卡由 `renderRun()` 按 `state.day` 与 `state.run.daily` 单独渲染，位置在 `#exList` 之后、`#auxSec` 之前。
- 导入导出：计划 JSON 只带 `xStateToPlanDict(state)`，跑步处方不在计划里；`state.run` 由 `IMPORT_KEEP_KEYS` 原样保留，换计划不清跑步记录。
- 往返零格差：`Workouts` 没变，xlsx 往返判据不受影响；新增的只是 `state.run` 这个本地键。
- CSV 26 列：`unifiedRecords()` 不读取 `state.run`，列数与列名零变化。

### 3.2 为什么不是「Workouts 的又一种行类型」

即使把跑步行放进 `Workouts`，`Day` 的完成度、T1/T2/T3 分层、进阶规则、`row_idx` 与 e1RM 关联都会得到一条没有 `load_kg` 的异类行；而需求书 §10 明确「不许用组数/1RM 口径写跑步处方」。用独立表（未来的 `RunPlan`）比用异类行更干净。

## 4 · 记录侧：并存而不互相污染

| 链路 | 跑步怎么处理 | 理由 |
|---|---|---|
| 日卡完成度 | 力量 `doneSets` 照旧；跑步卡自带 `done`，不并入「0/6」 | 两类完成度语义不同，合并会掩盖任一侧未完成 |
| 训练日志 / CSV | 跑步不进 `unifiedRecords()`，CSV 仍 26 列 | 冻结协议；跑步记录不是力量组 |
| JSONL 日志 | 同样不写入 | 与 CSV 同源，避免第二轮口径分叉 |
| e1RM | 只从 SBD 锚点动作取；跑步永不写 `e1rmLog` | 跑步没有 1RM 语义 |
| 吨位 / 容量 | 只统计 `load>0` 的力量行；跑步另算 `runKm / runMin` | 防止吨位被「0kg × 距离」拉低 |
| 跑量统计 | 从 `state.run.logs` 现算，独立显示在跑步卡与周总结的跑步段 | 与力量容量并列，不相加 |
| 整机备份 | `state.run` 在 `WORK_KEYS` 内，随账本分片与启动信封一起走 | 换机/恢复不丢跑步 |

### 4.1 三个键名单

- `WORK_KEYS`：16 → 17，加 `'run'`。
- `IMPORT_KEEP_KEYS`：加 `'run'`（换计划保住跑步记录）。
- `PLAN_OWNED_KEYS`：**不加** `'run'`（跑步不是计划本体，换计划不许清）。
- `SCHEMA_STAMP`：**不动**。`state.run` 是纯加法键，`ensureShape()` 末尾 `state.run = runNormalize(state.run)` 兜底；缺键回落默认，不阻断启动。
- `runNormalize()` 必须「任何异常都返回可用空结构」，不许抛错阻断启动。

## 5 · 门禁：哪些断言能把「写丢 / 算错」抓成红

### 5.1 静态守卫（建议编号 S53）

一条检查、六条腿：

1. `RUN_PLAN` 在模板里只定义一次，且恰好 9 项；
2. `state.run` 在 `WORK_KEYS` 与 `IMPORT_KEEP_KEYS` 内，且不在 `PLAN_OWNED_KEYS`；
3. `CSV_COLS` 仍 26 项且不含任何 `run_*` 列；
4. `renderRun` 在 `renderAll()` 与 `setLang()` 的非 AUX 分支各被调用一次；
5. 跑步卡可见文案无 RPE，且全部走 `L('中文','English')`；
6. `runNormalize` 在 `ensureShape()` 内被调用一次。

> 编号以 `gate.py` 实际输出为准；若 0.75 已占用 S53，顺延，不在文档里手抄。

### 5.2 动态断言 RUN1–RUN8

| ID | 断言 | 能抓的故障 |
|---|---|---|
| RUN1 | `runPlanOf(1/5/9/99)` 按周取值并正确夹紧；减载周次数下降 | 处方针错位 / 越界崩 |
| RUN2 | `reps×300m`、总工作秒、配速、跑步机 km/h 全部正确 | 换算系数写错 |
| RUN3 | `runZone()` 在 HRmax=190 的五个边界值判定正确；空心率返回 `''` | 区间边界错 / 无心率乱判 |
| RUN4 | 打卡写入 `logs['w-d']`，字段齐全、`done=true` | 字段漏写 / 键错位 |
| RUN5 | 撤销只改 `done`，记录与字段不丢 | 撤销把整条删掉 |
| RUN6 | 重新渲染/读回后逐字节一致 | 渲染丢数据 |
| RUN7 | 导入新计划后 `run` 仍在 | `IMPORT_KEEP_KEYS` 漏注册 |
| RUN8 | CSV 导出仍 26 列且不含 run 列 | 误把跑步塞进 CSV |

### 5.3 先证明能红

每条新断言至少做一次反向注入：

- 改 `RUN_PLAN[5].interval.reps` → RUN1 红；
- 把 `300/sec*3.6` 改成 `*3.3` → RUN2 红；
- 把 Z2 上界 70% 改成 71% → RUN3 红；
- `runToggleDone` 撤销时重建整条 → RUN5 红；
- 从 `IMPORT_KEEP_KEYS` 删 `'run'` → RUN7 红；
- 往 `CSV_COLS` 加 `run_dur` → RUN8 / S53 红。

验证记录写进对应提交说明（AGENTS §2.6）。

## 6 · 版本落点：为什么是 v0.80

- **v0.70** 已出包，承载器械身份 + 插片档位表（器械档案模型 + 启动阻断 + 四分片导出）。这是本周期最大的一次数据模型手术，不能再叠第二块高风险缝。
- **v0.75** 先收「记录链可信」：RPE 不凭空预填、关闭编辑不静默丢、徽章与账本 e1RM 同源。跑步要把记录写进账本，必须建立在「账本本身不丢数」之上。
- **v0.80** 跑步 v1 落在自己的节点：新增 `state.run`、DAY B/D 卡片、RUN1–RUN8 与真机证据。出包、装机、Release 与站点同步单独做一轮，问题可回滚。
- **v0.84+** 若用户要「计划里改跑步」，再加第 9 张表 `RunPlan`；不在 v0.80 一次做到位。

顺序理由一句话：**先修账本，再扩数据；先能记录，再谈可编辑。**
