## 0. 一页结论

| # | 决策 | 理由 |
|---|---|---|
| 1 | 器械身份与插片档位表都存本机 `state.gearProfile`，归 **prefs 分片**（PREF_KEYS + IMPORT_KEEP_KEYS），**不进 WORK_KEYS** | 这是「我这儿有什么器械」，不是「这周练什么」；换计划不能清、清账本不能带走、CSV/六表不能导出 |
| 2 | key = `场地 id + 动作 mv`，按场地隔离；另设 `fallback[mv]` 做「设为通用」 | 同一动作在商业店与家里是两台机器；`resolveVenueId(e)` 已经是现成的场地解析入口 |
| 3 | 身份 = 一组部件卡片，每张卡固定 `brand / series / name` 三个字段，层级由 kind 决定 | 复用装备库 `equipment.fields` 的同一套词，不发明第二套命名 |
| 4 | 插片档位表 = 每栈一份**显式升序 kg 列表**，不再用 `base + pin × inc`；用户可整台机器增删档位、分段生成、模板导入 | 非等差（前段 2.5、后段 3.5）无法用单一 `incKg` 表达 |
| 5 | 求解「最接近档位」：单栈取绝对差最小，平手取**低档**；双栈取笛卡尔和最小，平手取低总和、再取更均衡的 `max(i,j)`、再取低索引 | 低档更保守，且与现有哑铃吸附「严格小于才替换」的口径一致；双栈不出现一侧空载 |
| 6 | `stepKgOf(stack)`：单栈 = 相邻档最小差；双栈 = 全部相邻档差的 gcd。± 按钮不再按固定 kg 加，而是**走到相邻可达档** | gcd 可能是 0.5（2.5 与 3.5 的 gcd），按 0.5 加会造出不存在的重量 |
| 7 | 没有档位表时**不假装等差**：`solveLoad` 返回 `exact=false` + 「该动作未登记配重档位表」，主数字按输入直读 | 静默假设 2.5 会在第一台 3.5 机器上算错，且用户看不出来 |
| 8 | 旧存档（`schemaVer<9` 或带 `gearDefaults`/`stackCfg`）→ `markBootFatal('incompatible_gear')`，只读阻断；导出原始全部分片后才允许「导入新计划 / 新建空白档案」 | 不迁移、不降级、不落空账本；破坏性动作必须二次确认 |
| 9 | `e.gear` 只保留**便携参数**；`identity`/`stack`/`stackPins`/`manualKg` 不进计划 Gear 表 | 身份与档位是机器事实，换设备/换场地必须重新登记，不能随计划搬走 |
| 10 | 现有 `gearDefaults` 整套退役，不做兼容读 | 它同时在 WORK_KEYS 与 IMPORT_KEEP_KEYS，且每次改一个字段就把整份 `e.gear` 快照写进去，已经污染；留着就是第二份真相 |

## 1. 现状基线（执行者先理解为什么改）

### 1.1 当前器械默认的存法

- `state.gearDefaults[mv]` 是「同动作默认器械」。
- 它在 `WORK_KEYS` 里，也在 `IMPORT_KEEP_KEYS` 里，不在 `PREF_KEYS` 里。
- `setGearField()` 每改一个字段就执行：

  ```js
  state.gearDefaults[e.mv] = Object.assign({}, e.gear);
  ```

  也就是说：改一次销位，整份动作级 `e.gear`（含 barKg / collar / stackCfg / pin / lever / label …）都被复制成全局默认。用户只改了一个当次销位，却把「这个动作以后默认用几号销」也改了。
- `setGearGuess()` 同样把整份 `gearOf({mv})` 写进 `gearDefaults[mv]`。
- `gearOf(e)` 的优先级是：`e.gear` → `gearDefaults[mv]` → 场地 inventory → 契约 defaults。
- `migrateStateV7` / `migrateStateV8` 还会读写 `gearDefaults`，模板里另有几处兼容逻辑。

结论：**它既不是纯偏好，也不是纯账本，还是个整份快照的写入口**。本版直接退役，不做兼容读。

### 1.2 当前插片模型

- `e.gear.stackCfg = [{baseKg, incKg, pin}, …]`，`stacks` 为 1 或 2。
- 总重 = `Σ (baseKg + pin × incKg)`。
- `stepKgOf(stack)` = `gcd(inc_1 … inc_n)`。
- `solveLoad()` 在 stack 分支里总是 `exact=true`，只在 `|achieved-raw|>0.0005` 时给「按插销实际是 X」的警告。
- 编辑器 `renderGearStackCfg()` 每栈三个数字输入：基数 / 增量 / 销位；`renderGearStackBar()` 画竖向配重堆。
- 本地计算器 `LC_FIELDS` 是**临时草稿**，明确不持久化、不进 prefs/账本/CSV；不要把它和本次的「本机档位表」混为一谈。

### 1.3 当前分片与门禁事实

- `PREF_KEYS` / `WORK_KEYS` 的实际键数现场数模板里那两个数组（本文写作基线的是快照值），`mergeSlices()` 只把 `PREF_KEYS` 里的键从 prefs 分片搬进来。
- `SCHEMA_STAMP=8`；启动接受 `sv===8 || 7 || 6 || 5 || 4 || 3`。
- `savePrefsOnly()` **没有 READONLY 闸门**，而 `flushSave()` 有。这是一个现存漏洞：阻断态下任何 `savePrefsOnly()` 调用仍会写 prefs 分片。本版必须一并修。
- `gate.py` S39 目前钉住：`venues`/`activeVenueId` 双登记、v8 迁移闸门在位、`migrateStateV8` 内部串 `migrateStateV7`、四份旧契约哈希 == git HEAD。本版会拆掉迁移，S39 的判定必须**显式改**，不能悄悄删。
- `gearv.js` G3.6 / G9 / G10 与 `v3v.js` M10、`_sabotage_c3.py` / `_sabotage_m12.py` / `_sabotage_n2.py` 都直接引用 `gearDefaults` / `stackCfg`，全部要跟着改。

# A. 器械身份模型

## A1. 分层

```
场地（venue）
  └─ 动作档案（record，key = 场地 id + 动作 mv）
       ├─ kind：六类引擎 kind 之一（last confirmed）
       ├─ identity：部件卡片组
       │    ├─ machine   器械本体（插片机 / 挂片机 / 自重站 / 特殊器械）
       │    ├─ bar       杠铃杆
       │    ├─ plates    杠铃片
       │    ├─ support   架子 / 台子（含 type）
       │    ├─ dumbbell  哑铃
       │    └─ bench     哑铃凳（可选）
       ├─ params：本机默认参数（barKg / posts / stacks / lever …）
       └─ stack：本动作这台插片机的档位表（仅 kind=stack）
```

身份不是自由文本，也不是一个 `label`。它由**部件卡片**组成，每张卡只有三个字段：`brand`（品牌）、`series`（系列/产品线）、`name`（名字/型号）。这与 `RPL-Gear-v1.json` 的 `equipment.fields` 完全同词，避免「装备库叫品牌/系列/名字，器械叫厂商/型号/别名」这种第二套命名。

## A2. 记录结构

```jsonc
state.gearProfile = {
  "v": 1,
  "byVenue": {
    "<venueId>": {
      "<mv>": {
        "v": 1,
        "kind": "barbell",              // 六类之一；可被 e.gear.kind 覆盖
        "identity": {
          "machine":  { "brand": "", "series": "", "name": "" },
          "bar":      { "brand": "", "series": "", "name": "" },
          "plates":   { "brand": "", "series": "", "name": "" },
          "support":  { "type": "rack", "brand": "", "series": "", "name": "" },
          "dumbbell": { "brand": "", "series": "", "name": "" },
          "bench":    { "brand": "", "series": "", "name": "" }
        },
        "params": {                     // 只放可继承的默认参数；不含销位
          "barKg": 20,
          "collarOn": true,
          "collarPairKg": 5,
          "sides": 2,
          "incrementKg": 2.5,
          "variant": "standard",
          "posts": 2
        },
        "stack": null,                  // kind !== 'stack' 时省略或 null
        "updatedAt": "2026-11-07T10:40:00+08:00"
      }
    }
  },
  "fallback": {                         // 场地无关的「通用档案」，显式点「设为通用」才写
    "<mv>": { /* 同 record */ }
  }
}
```

`params` 是白名单的并集，**按 kind 只写相关键**：

| kind | 实际会写的 params |
|---|---|
| `barbell` | `barKg / collarOn / collarPairKg / sides / incrementKg / variant / posts` |
| `plate` | 上述中适用的 + `baseKg`（挂片机底重） |
| `stack` | `stacks / variant`（`baseKg` 不写；底重已含在 `levels[0]`） |
| `dumbbell` | `incrementKg / count`（按需） |
| `bw` / `special` | `label / unitKg / count / lever`（按需） |

未写的键由 `gearOf` 依次回落到场地 inventory 与契约 defaults；`identity` 同理，只写适用部件，不适用键直接省略，不存空卡。

`kind=stack` 时：

```jsonc
"stack": {
  "v": 1,
  "ladders": [                          // 长度必须 == params.stacks（1 或 2）
    {
      "v": 1,
      "levels": [20, 22.5, 25, 27.5, 30, 33.5, 37, 40.5, 44, 47.5],
      "updatedAt": "2026-11-07T10:40:00+08:00"
    }
  ]
}
```

关键取舍：

- `levels` 存**绝对 kg**（含机器底重），不存 `baseKg`/`incKg`。这样非等差不需要第二套解释。
- 第一档可以是 0，也可以是最低配重 20；求解与显示都按这个数。
- `pin`（当前销位）**不在 record 里**。它是每次训练的选择，存在动作行 `e.gear.stackPins`；record 只描述机器。
- `updatedAt` 用于「沿用上次同 kind 档案」的排序与排障，不参与求解。

## A3. 字段清单

| 路径 | 类型 | 必填性 | 边界 | 说明 |
|---|---|---|---|---|
| `gearProfile.v` | int | 结构必填 | 必须 `1` | 结构版本；不等于 `SCHEMA_STAMP` |
| `gearProfile.byVenue` | object | 结构必填 | 键为已有 venueId | 场地隔离的主表 |
| `gearProfile.fallback` | object | 结构必填（可为空） | 键为 mv | 「设为通用」的场地无关档案 |
| `record.v` | int | 必填 | 必须 `1` | 单条档案版本 |
| `record.kind` | enum | 可选 | 六类 kind | 上次确认的器械类型；`e.gear.kind` 优先 |
| `record.identity` | object | 可选 | 只认六个部件键 | 未登记时可为空对象 |
| `identity.<component>.brand` | string | 可选 | trim 后 ≤ 24 | 品牌 |
| `identity.<component>.series` | string | 可选 | trim 后 ≤ 24 | 系列/产品线 |
| `identity.<component>.name` | string | 可选 | trim 后 ≤ 32 | 名字/型号 |
| `identity.support.type` | enum | 可选 | `rack` / `bench` / `platform` / `combo` | 架子/台子类型 |
| `record.params` | object | 可选 | 只允许白名单键 | 见 §A5 |
| `record.stack` | object | kind=stack 时必填 | 见 B 节 | 插片档位表 |
| `record.updatedAt` | string | 可选 | ISO 8601 | 仅记录 |

**必填性的唯一规则：**

1. 整个 `identity` 是可选的。不登记身份不妨碍记训练。
2. 单张部件卡「已登记」的判据是 `brand` 或 `name` 至少一个非空（`series` 单独填不算登记），与装备库「型号或品牌至少填一个」的口径一致。
3. 部件卡全部为空 ⇒ 身份视为「未登记」，UI 显示 `未登记（可选）`，不报错。
4. `support.type` 只在 `support` 卡已登记时有意义；未登记不强制选 type。
5. 不做「杠铃必须三张卡全填」的强制。用户可以先只登记杆，片和架子以后补。

## A4. kind × 字段矩阵

`✓` = 该 kind 会显示并可填；`○` = 可选；`—` = 不显示、不存储。

| kind | machine | bar | plates | support | dumbbell | bench |
|---|---|---|---|---|---|---|
| `barbell` 杠铃 | — | ✓ | ✓ | ✓（rack/bench/platform/combo） | — | — |
| `plate` 挂片 | ✓ | — | ✓ | — | — | — |
| `stack` 插片 | ✓ | — | — | — | — | — |
| `dumbbell` 哑铃 | — | — | — | — | ✓ | ○ |
| `bw` 自重 | ○（引体架/双杠站） | — | — | — | — | — |
| `special` 特殊 | ○（壶铃/药球/战绳等） | — | — | — | — | — |

与用户口径的对应：

- 插片 / 挂片 / 自重：品牌 + 系列 + 名字 → `machine` 卡。
- 挂片：再加杠铃片 → `machine` + `plates`。
- 杠铃：架子/台子 + 杆 + 片 → `support` + `bar` + `plates`。
- 哑铃：品牌/系列/名字，最多再加哑铃凳 → `dumbbell` + `bench`。

`plate` 的 `plates` 卡与 `barbell` 的 `plates` 卡是两张独立卡。同一套片可以在录入时一键「沿用上次同 kind 的片卡」，但不会隐式联动。

## A5. 存储位置、key 设计与为什么

### A5.1 key

```
state.gearProfile.byVenue[venueId][mv]
```

- `venueId` 取 `resolveVenueId(e)` 的结果，不是硬取 `state.activeVenueId`。这样计划里绑定了 `defVenueId` 的动作会用对应场地的机器；本机 `dayVenueId` 覆盖时跟着覆盖。
- `mv` 是动作库稳定 id（`rxlib.py` 的 id），不是界面标签。绝不能用中文名做 key。
- 不用 `venueId + '::' + mv` 扁平串：嵌套对象没有分隔符转义问题，导出/排障也更直观。
- `fallback[mv]` 只在「设为通用」时写；读取顺序：`byVenue[venue][mv]` → `fallback[mv]` → 同场地同 kind 最近一条（仅身份继承，见 A7）→ 空。
- **不做跨场地字段级合并**：场地记录存在就整条用它，避免把 A 店的杆和 B 店的片拼在一起。
- **一个 `mv` 在一个场地只对应一台机器**。如果同一场地同一动作确实有两台不同的机器（例如两台坐姿划船），应在动作库侧拆成两个 `mv`（数据源改名/新增），不要在本层把 record 做成机器列表。这条要写进实现注释，防止后来者把 `byVenue[venue][mv]` 改成数组。

### A5.2 分片归属

| 名单 | 是否加入 | 原因 |
|---|---|---|
| `PREF_KEYS` | 加入 `gearProfile` | 器械环境是偏好，不是训练账本；`savePrefsOnly()` 就能落盘 |
| `IMPORT_KEEP_KEYS` | 加入 `gearProfile` | 换计划不能把用户登记过的机器与档位清掉 |
| `WORK_KEYS` | **不加入**，并移除 `gearDefaults` | 清账本/导出账本不应带走器械环境 |
| `PLAN_OWNED_KEYS` | 不加入 | 计划不拥有本机机器档案 |
| `PLAN_SCHEMA` / Gear 表 | 不加入 | 见 A6，身份与档位不进计划 |

### A5.3 为什么不用现成的 `venues[id].machines[]`

`venues[id].machines[]` 是「这台场地里有什么机器」的盘点点，字段是 `name/kind/qty/note`。本次的 record 是「这个动作这次用哪台机器 + 这台机器的档位」，两者生命周期不同：

- 盘点表可以一台机器挂多行、可以没有档位、可以只有名字；
- record 必须跟着动作 mv 走，并且档位要能被求解器读取。

因此**不把档位塞进 `machines[]`**。但可以把盘点表作为身份录入的「快选来源」：契约 v2 给 `machines_optional` 增加 `brand`、`series`；用户点选一台机器时，把 `brand/series/name` 快照进 record。快照之后两边独立，盘点表改名不会静默改历史记录；需要同步时点「从清单刷新」。

### A5.4 写入路径（这是治「污染」的关键）

把写入拆成三类，任何一类都不许写整份快照：

| 操作 | 写哪里 | 不写哪里 |
|---|---|---|
| 改 barKg / kind / posts / stacks / lever / label / unitKg / count / baseKg（plate） | `e.gear` 对应字段 + `profile.params` 对应**单字段** | 不写 `manualKg`、不写 `stackPins`、不写 identity/stack |
| 改销位 / 手动总重 / 当日场地绑定 | 只写 `e.gear.stackPins` / `e.gear.manualKg` / `e.gear.dayVenueId` | 不写 `profile` |
| 保存身份 / 保存档位表 / 设为通用 | 只写 `profile.identity` / `profile.stack` / `profile.fallback` | 不写 `e.gear` |

实现落点：

- `setGearField(patch, opts)` 改为：先合并进 `e.gear`；再对 `patch` 里属于 `DEFAULTABLE_PARAM_KEYS` 的键，逐键写 `profileEnsure(venue,mv).params[key]`。**不再 `Object.assign` 整份。**
- `setGearStackField(i,'pin',v)` / `setGearStackPin()` 改为写 `e.gear.stackPins[i]`，不再写 profile。
- `setGearStacks(v)`：`stacks` 写 profile.params；`stackPins` 跟着截断/补 0，只写 `e.gear`。
- `setGearGuess(mv,kind)`：只写 `profile.kind`，不再写整份 `gearOf()`。
- `gearDefaultOf(mv)` 删除，换成 `gearProfileOf(venueId,mv)` + `gearProfileParams(mv)`。

`DEFAULTABLE_PARAM_KEYS` 建议白名单：

```js
['kind','barKg','collarOn','collarPairKg','sides','incrementKg','variant',
 'posts','baseKg','stacks','lever','label','unitKg','count']
```

`manualKg`、`stackPins`、`dayVenueId` 永不进 profile。

### A5.5 可恢复默认的路径

这是用户点名要的，必须显式提供，且都不碰训练账本：

| 入口 | 行为 | 影响面 |
|---|---|---|
| 身份页「清除身份」 | 删除当前 `record.identity` | 只影响身份显示，不影响重量 |
| 档位页「清空档位表」 | 删除当前 `record.stack`，求解退回「未登记」警告 | 只影响插片动作的吸附 |
| 动作页「清除本机档案」 | 删除 `byVenue[venue][mv]`；若 `fallback[mv]` 存在，提示将回落到通用档案 | 参数、身份、档位一起回默认 |
| 设置 · 场地与器械「重置全部器械档案」 | 删除 `gearProfile.byVenue` 与 `fallback`，保留 `venues`/inventory | 全部动作回契约/场地默认；不动计划与账本 |
| 设置「从通用档案恢复」 | 把 `fallback[mv]` 复制回当前场地 | 单动作恢复 |

注意边界：全局重置**不能**清掉计划里随附的 `e.gear` 便携参数。如果某个计划行自带 `barKg=15`，重置档案后它仍会赢。要彻底回默认，应重新导入计划或点该动作的「清除本机覆盖」（`gearSource='local'` 时删除 `e.gear` 的本机键）。这条要写进确认弹窗，不许含糊。

## A6. 与 `e.gear`、场地库存的合并优先级

`gearOf(e)` 的新优先级（从高到低）：

1. `e.gear`（计划随附的便携参数，或本机一次性覆盖）
2. `profile.params`（本机同动作默认）
3. `venueInv(resolveVenueId(e))`（场地库存：杆重、片重、赛扣、哑铃档）
4. `GEAR_SCHEMA.defaults`

`kind` 单独一条：`e.gear.kind` → `profile.kind` → `gearKindGuess(mv)` → `kind_default`。
`stackPins`：只读 `e.gear.stackPins`；没有就让求解器自动选最近档，**不回读 profile**。
`identity` / `stack`：只读 profile，永远不从 `e.gear` 读。

### A6.1 `e.gear` 的便携 / 本机字段

| 类别 | 键 | 进计划 Gear 表？ | 说明 |
|---|---|---|---|
| 便携 | `kind`, `barKg`, `collarOn`, `collarPairKg`, `sides`, `incrementKg`, `variant`, `posts`, `baseKg`, `stacks`, `lever`, `label`, `unitKg`, `count`, `defVenueId` | 是 | 计划作者可以规定「这个动作用 15kg 杆」 |
| 本机 | `stackPins`, `manualKg`, `dayVenueId` | 否 | 销位/当日实称/当日场地；换设备没有意义 |
| 禁止 | `identity`, `stack`, `stackCfg` | 否 | 机器事实；`stackCfg` 是旧格式，导入时必须报错 |

落点：

- `xGearCanonical(gear)` / `xGearFromState()` 导出前按 `GEAR_SCHEMA.portable_gear_keys` 过滤；把本机键剥掉。
- `xValidateGear()` 导入时检查：出现 `stackCfg` → error「旧版插片配置不支持，请用新版重新导出计划」；出现 `identity`/`stack`/`stackPins`/`manualKg`/`dayVenueId` → error「本机字段不得随计划导入」；出现白名单外未知键 → error（契约 v2 定义白名单，Python/JS 共读）。
- Python `plan_xlsx.py` 的 `_validate_gear` 同样按 `portable_gear_keys` 验，不许只验 kind/source。

## A7. 录入界面：怎么做到「默认继承、只改差异」

### A7.1 入口

- 动作编辑器 · 器械区顶部新增一行 `#gearIdentity`：
  - 摘要：`器械：Technogym Selection 坐姿划船` / `杆：Eleiko IPF · 片：Eleiko` / `未登记（可选）`
  - 右侧 `编辑身份` 打开身份面板。
- 身份面板是当前编辑器风格的整屏/底部面板，不引入新框架。
- 身份不在主训练卡片上占行；主卡只在器械行尾显示一个短标签（优先 `name`，没有则 `brand`），点击进身份面板。避免品牌+系列全串把卡片撑破。
- **身份标签不放进配重图区**。配重图区继续遵守既有外显规则：只显示图形、不加任何具体文字、不靠缩字号/截断消溢出；身份是器械区的元数据，放在图区之外。

### A7.2 继承顺序（打开面板时预填）

1. `byVenue[当前场地][mv]` 存在 → 整条预填。
2. 否则 `fallback[mv]` 存在 → 整条预填，标 `通用档案`。
3. 否则同场地里**同 kind、更新时间最新**的一条 → 只复制 `identity`，标 `沿用自 <动作名>`。
4. 否则空白。

规则：

- 继承只发生在**打开面板时**，不在保存时偷偷合并。
- 字段预填后，用户只改差异；未改的字段保持继承值。
- 面板顶部显示来源徽章，用户知道自己在改谁的值。
- **档位表不参与自动继承**。不同机器即使同为插片，档位也可能完全不同；自动搬档位表会静默算错重量。新动作的档位表初始为「未登记」，给 `生成 / 导入 / 从其他动作复制` 三个显式入口。

### A7.3 面板信息结构

按 kind 只渲染相关卡，顺序固定：

- `barbell`：杆 → 片 → 架子/台子
- `plate`：机器 → 片
- `stack`：机器
- `dumbbell`：哑铃 → 凳（可选）
- `bw` / `special`：机器/站位（可选）

每张卡：

```
[部件名]                      [沿用上次] [清空]
品牌 [__________]  系列 [__________]  名字 [__________]
```

- 三个输入都 `inputmode="text"`，`maxlength` 按契约；回车/失焦即校验，不弹大模态。
- 卡内全空 = 未登记；只有系列 = 未登记（提示「再填品牌或名字」）。
- 底部：`恢复默认`（删本记录身份）、`设为通用`（写 fallback）、`保存`。
- 保存只写 `identity`，不碰 params/stack。

### A7.4 不烦人的四条硬规则

1. **不阻塞记录**：身份为空也能正常记组；不弹「请先登记器械」。
2. **不重复问**：同一场地同一动作第二次打开直接预填，零输入即可保存。
3. **不整份覆盖**：改一个字段只写一个字段；「沿用上次」不是「复制整条并覆盖」。
4. **不隐式跨机器**：身份可以跨动作沿用，档位表不可以；复制档位必须用户点「复制」。

### A7.5 从场地盘点表快选（可选但推荐）

- 场地页 `machines[]` 增加 `brand/series` 后，身份面板的机器卡旁出现 `从本场地清单选择`。
- 选中后快照 `brand/series/name` 进 record，并记 `origin:{type:'catalog', ref:'<machine id>'}`；不建立活链接。
- 盘点表后续改名不静默改历史记录；要同步点 `从清单刷新`。

# B. 插片配重曲线（非等差）

## B1. 数据结构

```jsonc
// record.stack（仅 kind=stack）
{
  "v": 1,
  "ladders": [
    {
      "v": 1,
      "levels": [20, 22.5, 25, 27.5, 30, 33.5, 37, 40.5, 44, 47.5],
      "updatedAt": "2026-11-07T10:40:00+08:00"
    }
  ]
}
```

约束（写进 `RPL-Gear-v2.json` 的 `stack.ladder`，Python/JS/gate 共读）：

| 约束 | 值 | 失败处理 |
|---|---|---|
| `levels` 长度 | 1 … 60 | 编辑器拒绝保存；启动标记 invalid |
| 升序 | 严格递增 | 拒绝保存；不自动排序 |
| 每档 kg | 有限数，≥ 0，≤ 500 | 拒绝保存 |
| 相邻最小差 | ≥ 0.25 | 拒绝保存 |
| 重复档 | 禁止 | 拒绝保存 |
| `ladders` 长度 | 必须等于 `params.stacks`（1 或 2） | 保存时校验；求解时警告 |
| `pin` 索引 | `0 … levels.length-1` | 读取时钳制并警告，不静默改 record |

单位只支持 `kg`。v0.70 不做 lb；契约里不预埋 `unit` 字段，避免半成品。

## B2. 存储与 key

- 档位表属于 `state.gearProfile.byVenue[venueId][mv].stack`，归 **prefs**。
- 每个栈一份 `ladders[i]`；`stacks=2` 时两份独立，长度可以不同。
- 当前选择 `e.gear.stackPins = [i, j]`（0 基索引），属于账本/计划行，不写 profile。
- 为什么按动作而不是按机器：用户明确要求「每个动作单独本地存储，不同动作的插片配重都不一样」。同一台机器被两个动作共用时，本版让两份表独立；要同步用「复制到其他动作」。这是刻意取舍，弹窗里要写明，避免用户以为改一处两边都变。

## B3. 「最接近档位」求解

### B3.1 定义

- 单栈：可达集合 = `levels`。
- 双栈：可达集合 = `{levelsA[i] + levelsB[j]}`。
- 目标是 `e.load` 的数值化结果（现有 `solveLoad` 里的 `raw = +(e.load)||0`），不是处方文本；`3×5+` 里的 `+`、RPE 备注、百分比都不参与吸附。
- 目标是 `e.load`（输入值），**不被静默改写**。

### B3.2 算法

```
snapStack(target, ladders):
  if ladders.length == 1:
    逐档 |level - target|；平手取较小 level
  if ladders.length == 2:
    遍历所有 (i,j)：
      score = |A[i] + B[j] - target|
      平手：取较小的 A[i]+B[j]
      再平手：取较小的 max(i,j)（两栈更均衡，不出现一侧空载）
      再平手：取较小的 i，再取较小的 j
  返回 { pins:[i,...], achieved:sum, exact:|sum-target|<0.001,
         delta:sum-target, reason:'below'|'above'|'' }
```

复杂度：单栈 ≤ 60 次；双栈 ≤ 60×60 = 3600 次。每张卡一次，30 张卡约 10 万次比较，可接受。若后续卡数变多，再按 `mv + ladder.updatedAt + target` 做小缓存；v0.70 不预做。

### B3.3 平手取低档 / 取均衡的理由

- 与现有哑铃吸附 `Math.abs(b-side)<Math.abs(a-side)`（严格小于才替换，等于保留先出现的低档）一致。
- 训练场景下，少 1–3.5 kg 比多 1–3.5 kg 更保守；尤其减重期与伤病期。
- 双栈在同总和下取 `max(i,j)` 更小的一对，避免自动吸附给出「一侧 0 片、另一侧满载」的怪组合；用户仍可手动点任意组合。
- 需要冲顶时，用户在配重堆上直接点更高一档即可；自动吸附只负责「最接近」，不替用户做冲顶决定。

### B3.4 明确警告，不静默

`solveLoad` 的 stack 分支返回：

- `exact=true`：`|achieved-target| < 0.001`
- `exact=false` 且 `achieved < target`：`最近档 X kg（差 -Y）`
- `exact=false` 且 `achieved > target`：`最近档 X kg（差 +Y）`
- 目标低于最低档：`低于机器最低档 X kg`
- 目标高于最高档：`高于机器最高档 X kg`
- 没有档位表：`该动作未登记配重档位表（按输入直读）`，`exact=false`
- 档位表 invalid：`档位表损坏（第 N 条）`，`exact=false`

所有文案走 `L()` 双语。`warnings` 是数组，UI 不合并成一句含糊的「重量不准」。

### B3.5 例子（可直接做成回归用例）

档位：`[20, 22.5, 25, 27.5, 30, 33.5, 37, 40.5, 44, 47.5]`（前段 2.5，后段 3.5）

| 目标 | 最近档 | Δ | 说明 |
|---|---|---|---|
| 36 | 37 | +1 | 37 比 33.5 更近 |
| 35 | 33.5 | -1.5 | 33.5 差 1.5，37 差 2 |
| 35.25 | 33.5 | -1.75 | 与 37 等距，平手取低档 |
| 15 | 20 | +5 | 低于最低档，警告 |
| 50 | 47.5 | -2.5 | 高于最高档，警告 |
| 30 | 30 | 0 | exact=true |

双栈例：A=`[0,2.5,5,8.5]`，B=`[0,2.5,5,8.5]`

| 目标 | 组合 | Δ | 说明 |
|---|---|---|---|
| 10 | 5+5 | 0 | exact=true |
| 6 | 2.5+2.5 | -1 | 总和 5 最近；5+0 / 2.5+2.5 / 0+5 同和，取 max(i,j) 更小的均衡组合 |
| 4 | 2.5+2.5 | +1 | 总和 5 最近（比 2.5 近）；同样取均衡组合 |

## B4. 取整、步长、± 按钮

### B4.1 `stepKgOf(stack)` 新口径

写进契约 v2 的 `step_rule.stack`：

```
单栈：相邻档差的最小值
双栈：所有相邻档差的 gcd
无档位表：no_stock_fallback（2.5）
```

为什么单栈不用 gcd：`levels=[0,2.5,5,8.5]` 的相邻差是 2.5/2.5/3.5，gcd 是 0.5，但 0.5 kg 根本不可达。用最小差 2.5 才是这台机器的真实分辨率。
为什么双栈用 gcd：两栈的和可以组合出更细的格子（例如 2.5 与 3.5 的 gcd 0.5），`mround` 用它做粗取整，最后仍由 `snapStack` 吸附到真实可达和。

### B4.2 `mround` 的边界

- 现有 `mround(v,s)` 保持不变；stack 传入新的 `stepKgOf`。
- `mround` 只负责「处方文本/热身/伤病调整」的粗取整，**不负责**最终机器可达性。最终可达性一律由 `solveLoad` 的 `snapStack` 给出，`exact` 与警告一起返回。
- 伤病影子 `injuryShadowOf(e)` 里的 `after=...`：stack 用 `snapStack(目标值)`，取 `achieved` 作为 `after`；非 stack 继续 `mround`。
- 热身 `warmups`：建议对 stack 的每一档做 `snapStack` 显示；若时间不够，至少保留求解器警告，不许把不可达值直接写成处方。

### B4.3 ± 按钮

- 契约 `step_buttons` 的 `count=4`、`onclick=stepLoad(±1/±2)` 不变，S38 的调用形状不变。
- 内部：
  - 非 stack：`delta=mult*stepOf(e)`，与今天一致。
  - stack：`nextReachable(e, dir, mult)`：在当前可达集合里，找到比当前 `achieved` 大/小的第 `mult` 个**不同总和**；返回 `{load, pins}`。同时写 `e.load`（或编辑器草稿）与 `e.gear.stackPins`。
  - 到顶/到底：钳制并 haptic，不循环。
- 按钮文案：stack 不再显示固定 `±stepOf(e)`，改为显示**本次实际跨过的差**（如 `+3.5` / `-2.5`），或者在没有档位表时显示裸 `+`/`−`。这需要改 `gate.py` S38 的 `card38` 字符串断言（见 D3）。

### B4.4 显示口径

- 主数字显示 `achievedKg`（机器实际）。
- 输入值只在差开时以小字并列显示 `输入 X`。
- 差值统一写 `Δ +/−`，不写「差 1.5」这种没有方向的句子。

## B5. 与 `solveLoad` / `stepKgOf` 的衔接点

| 函数/位置 | 今天 | 本版改成 | 风险/断言 |
|---|---|---|---|
| `gearOf(e)` | `stackCfg=gearStackCfg(src,def,g)` | `stackPins = src.stackPins`（不读 profile） | G1 系列夹具全部要换 |
| `stepKgOf(g,inv)` | stack = `gcd(incs)` | 单栈最小差 / 双栈 gcd / 无表 fallback | 必须新增非等差用例 |

| `effectiveLoad(e)` | 继续用 `effectiveKg` | 语义不变；但 stack 的 e1RM/吨位建议改用 `achievedKg`（见下） | 需要用户拍板口径 |
| `stepOf(e)` | 返回 `stepKg` | stack 的 `stepKg` 只做粗取整；按钮改用 `nextReachable` | S38 文案断言要改 |
| `quickLoad(ev,i,mult)` | `e.load += mult*step` | stack 走 `nextReachable`，同时写 `e.load` 与 `stackPins` | 首页 G9 断言 |
| `stepLoad(mult)` | 改 `#edLoad` | stack 改草稿 `load` + 草稿 `stackPins`；保存才落账 | 编辑器 G9 断言 |

| `renderGearStackCfg` | 每栈 base/inc/pin 三个输入 | 只留栈数/龙门架 + `档位表（N 档）` 入口 + 当前销位 | G9 大改 |
| `renderGearStackBar` | 每档一块，块下写 `base+pin*inc=kg`；图区上方写 `实配 X kg` / `与输入差 Δ` | 窗口化渲染（当前销位 ±6 档），点块选索引；**图区只画块与销位，一个字都不写**；旧三处文字（`实配`、`Δ`、`#i base+pin×inc=kg`）随旧模型一起删除，不迁移 | 60 档不能全画；见 B6.6 外显规则 |
| `xGearCanonical` | 导出整份 `e.gear` | 按 `portable_gear_keys` 过滤 | Python 同步 |
| `xValidateGear` | 只验 kind/source | 拒绝旧 `stackCfg` 与本机键 | 导入明确失败 |
| `logT1MainE1rm` / 吨位 | 用 `effectiveKg` | **建议** stack/受限器械用 `achievedKg` | 需用户拍板，见 B5.1 |

### B5.1 e1RM 与吨位的口径（需用户拍板）

非等差吸附会把「目标 85 / 实配 80」的差距从 0.5 kg 放大到 3.5 kg。如果 e1RM 仍按 `effectiveKg`（输入值）记，用户会被记上一个没举起来的重量。建议：

- `solveLoad` 同时返回 `effectiveKg` 与 `achievedKg`（已有）。
- 新账本所有受限器械（stack / plate / barbell / dumbbell / special manual）的 e1RM 与吨位改用 `achievedKg`；`bw` 继续用净负荷。
- 这是口径变更，不只是器械功能；执行前必须让用户确认。若不改，至少在 UI 明示「按输入记，不按实配」，不许两边都含糊。

## B6. 档位编辑界面

### B6.1 信息结构

```
┌ 档位表 · 坐姿划船 ──────────────────────────┐
│ 场地：商业店 A · 插片 · 1 栈 · 共 10 档      │
│ 最小差 2.5 · 最大 47.5 kg                   │
├─────────────────────────────────────────────┤
│  #1   20.0 kg                     [当前]    │
│  #2   22.5 kg                               │
│  #3   25.0 kg                               │
│  …                                           │
│  #10  47.5 kg                               │
├─────────────────────────────────────────────┤
│ [+ 档位] [− 档位] [生成] [导入] [恢复模板]   │
│                              [取消] [保存]   │
└─────────────────────────────────────────────┘
```

- 双栈时顶部出现 `栈 1 / 栈 2` 切换；每栈独立列表。
- 查看模式：点一行 = 选当前销位（写 `e.gear.stackPins`，保存后落账）。
- 编辑模式（铅笔）：行内直接改 kg；改完即时校验。
- 当前销位用高亮 + `当前` 标签，不用文字长句。
- 不显示 `baseKg`/`incKg` 这两个旧概念；用户面对的是「这台机器每一档多少 kg」。

### B6.2 增删档位

- `+ 档位`：在当前行后插入，默认取相邻两档中点（若没有下一档，取上一档 + 最小差）；插入后进入编辑态。
- `− 档位`：删除当前行；删除前二次确认（防误触）；若删到只剩 1 档，允许但提示「只剩 1 档」。
- 删除/插入都只改草稿；点 `保存` 才写 profile。
- 上限 60 档；到上限禁用 `+` 并给一行提示。

### B6.3 生成器（整台机器一次成型）

两种模式，先生成预览，用户确认后才替换当前列表：

1. **等差**：`起始 kg` + `步长 kg` + `档数` → `[start, start+step, …]`。
2. **分段**（非等差的常用形态）：若干段，每段 `段内档数 × 段步长`，段间接续。例：
   - 段 1：10 档 × 2.5（20 → 42.5）
   - 段 2：8 档 × 3.5（46 → 70.5）
   - 预览显示「10 + 8 = 18 档，20 → 70.5 kg」。

生成器只负责写 `levels`，不写 `baseKg`/`incKg`，不维护「生成公式」作为运行时真相。保存后就是一份显式列表；以后手改一档不会被生成器回滚。

### B6.4 模板导入 / 复制 / 粘贴

- **内置模板**（契约 v2 `stack.ladder.templates`）：
  - `uniform_2_5`：0 起，2.5 步长，20 档
  - `uniform_5`：0 起，5 步长，16 档
  - `mixed_2_5_3_5`：前 10 档 2.5，后 8 档 3.5（对应「前段 2.5、后段 3.5」）
- **从其他动作复制**：列出同场地已登记档位表的动作；复制是**一次性快照**，之后两边独立。
- **从其他场地复制**：同上，跨场地列表；只复制档位，不复制身份与参数。
- **粘贴 kg 列表**：接受逗号/空格/换行分隔；解析后逐项校验；重复项报错而不是去重（去重会静默改机器事实）。
- 所有导入都走「预览 → 应用」，替换整表要二次确认。

### B6.5 校验与保存

- 保存前逐条校验 B1 表；任一失败：对应行标红、底部给具体原因、`保存` 禁用。
- 不自动排序、不去重、不四舍五入到 2.5；只做 `toFixed(3)` 的显示格式化。
- 保存成功写 `record.stack` + `updatedAt`，`savePrefsOnly()`；不写 workout 分片。
- 保存后回到动作编辑器，主数字立刻按新档位重算（`renderExercises()` 局部刷新即可，不整树重绘）。

### B6.6 外显规则（沿用既有配重 UI 硬约束，不得被本次改写破坏）

既有规则：**配重区外显只画图形；不写具体文字；溢出从信息层消除，不靠缩字号或截断；重量数字若保留必须放在不会溢出的位置（图区之外）。**

本版落地为：

| 位置 | 允许 | 禁止 |
|---|---|---|
| 图区（`gp-stacks` / 每栈的 `gp-stack` 画布） | 档位块、销位标记、选中态高亮、栈的分隔 | 任何文字：`实配 X kg`、`与输入差 Δ`、`#i base+pin×inc=kg`、品牌/系列/名字、`N 档` 之类 |
| 图区上方单行摘要（属于动作行的元数据带，不属于图区） | `档位 N · 范围 20–47.5 kg · 当前第 k 档`；身份标签 `品牌 系列 名字` | 长句、会随档数增长的文本 |
| 主数字（配重读数） | `achievedKg`；差开时并列小字 `输入 X` / `Δ ±Y` | 塞进图区内部当作块内文字 |

- `renderGearStackBar` 里的 `gp-stack-lbl` 两条（`实配` / `与输入差`）与块下那条 `#i base+pin×inc=kg` **整体删除**，不是搬到块里换个字号。旧 `base/pin/inc` 在这套新模型里已不存在，保留文字等于把退役字段带进 UI。
- 摘要行必须能容纳最坏情况（双栈 × 60 档 × 三位小数）而不换行溢出：用 `flex-wrap` 允许换行、或把 `范围` 缩成 `20–47.5` 这种区间写法；**不许**用 `font-size` 下调或 `text-overflow: ellipsis` 兜底。
- 点块选档时不弹气泡文字；选中态用描边/亮度变化表达，kg 值同步刷新到主数字与摘要行。
- 回归新增一条断言：`gp-stacks` 子树内 `textContent` 为空（只允许 `\s`），且不含 `实配|与输入差|×` 字面量。这条断言必须先在旧实现上跑红，再在新实现上跑绿（AGENTS §2.6「断言必须能红」）。

## B7. 缺失 / 损坏 / 边界

| 情形 | 求解行为 | UI | 是否写盘 |
|---|---|---|---|
| 无 `record.stack` | `achieved=输入`，`exact=false`，warning「未登记配重档位表」 | 主数字直读输入 + 琥珀色「登记档位」入口 | 否 |
| `record.stack` 结构坏（`ladders` 非数组） | 同上，warning 指向档案损坏 | 设置页徽章「有 N 条档案需修复」 | 否 |
| 某一 `levels` 非法 | 该记录标记 invalid；求解按无表处理 | 档位页打开即显示错误行 | 否 |
| `pins` 越界 | 读时钳制到 `0..len-1`，warning「销位已钳到最高档」 | 主数字显示钳后的值 | 否（除非用户手动选档） |
| `stacks` 与 `ladders` 长度不一致 | **不计算部分和**：`achieved=输入`，`exact=false`，warning「栈数与档位表不一致，无法计算」 | 档位页顶部红条，保存前必须修 | 否 |
| 目标低于最低档 | `achieved=最低档`，warning | 显示最低档 + Δ | 否 |
| 目标高于最高档 | `achieved=最高档`，warning | 显示最高档 + Δ | 否 |
| 用户改了档位表后旧销位超界 | 下次求解钳制；旧 `e.gear.stackPins` 不自动重写 | 首次进入给一次 toast | 仅用户点选/保存时 |

原则：**求解器是纯函数，不修数据**；所有修正要么由编辑器显式保存，要么只读钳制 + 警告。禁止在 `solveLoad` 里 `delete`/`push`/`sort`。

## B8. 性能与确定性

- 双栈 60×60 穷举是确定性的；不要用「先按目标对半再各自吸附」的贪心近似，会在非等差下给出次优解。
- 平手规则写死：低总和 → `max(i,j)` 更小 → 低 `i` → 低 `j`。回归用例要钉住，避免不同引擎的 `sort` 稳定性差异。
- 规模：最坏 200 个动作 × 2 栈 × 60 档 ≈ 100 KB 量级的 JSON；prefs 分片没有原生硬上限，但档位表只在用户点保存时写 `savePrefsOnly()`，不要在每个销位/输入事件里写全表。
- 如果未来 `stacks` 扩到 3，穷举退化为 60³；届时再改成分段 DP。v0.70 不做。

# C. 旧格式：明确失败，不迁移

## C1. 接受规则（正白名单，不是黑名单）

启动只接受：

```js

&& s.weeks && s.profile
&& gearProfileOk(s.gearProfile)     // v===1，byVenue/fallback 是对象
```

其余一律进入阻断页。**不做**以下任何事：

- 不把 `stackCfg` 转成 `levels`
- 不把旧账本补成空 profile 后继续
- 不在 `ensureShape()` 里给旧键补默认值

## C2. 检测点

| 检测 | 判据 | 处理 |
|---|---|---|
| 旧 schema | `schemaVer < 9`（含 3–8） | `markBootFatal('incompatible_gear')` |
| 旧器械默认 | `s.gearDefaults` 存在（哪怕是 `{}`） | 同上 |
| 旧插片字段 | 任一动作 `e.gear.stackCfg` 存在 | 同上（启动期扫描；导入期另报） |
| 新档缺 profile | `sv===9` 但 `s.gearProfile` 缺失/非对象/`v!==1` | 同上（这是混合/损坏档案，不能当新装机） |
| 单条档案坏 | `record.v` 不认识或 `stack` 结构坏 | 不阻断启动；标记 invalid，求解警告 |
| 旧单文件存档 | `rawL` 解析出 `v/schemaVer<9` | 同上，`src` 标明 `roast_state.json（旧版单文件存档）` |

`mergeSlices()` 之后就能看到 `s.gearProfile`（因为它在 PREF_KEYS 里），所以判定放在 `sv===9` 分支开头，早于 `ensureShape()` 与任何 `save()`。

## C3. 阻断页

沿用 `renderBootFail()`，新增原因与文案：

```
READ-ONLY · 存档未被改动

训练账本版本不兼容

```

1. `⤓ 导出全部分片原文`（新行为，见 C4）
2. `⧉ 复制全文`
3. `◎ 只读浏览`：**只做原始 JSON 的结构预览，不进入正常渲染、不跑 `solveLoad`**（旧 `stackCfg` 在新求解器里没有读法，硬渲染会报错）

`BF_REASON_LABEL` 新增 `incompatible_gear: '器械档案版本不兼容（不迁移）'`。

## C4. 导出必须覆盖全部分片

现有 `exportBootStore()` 只导出 `bootFatal.raw`（通常是 workout 分片）。旧 `venues` 在 prefs 分片里，只导 workout 会丢另一半。本版改为导出一个 JSON 信封：

```json
{
  "format": "RPL-BootBackup-v1",
  "exportedAt": "2026-11-07T...",
  "shards": {
    "prefs": "<原始文本或 null>",
    "workout": "<原始文本或 null>",
    "lib": "<原始文本或 null>",
    "archive": "<原始文本或 null>"
  },
  "bootFatal": { "reason": "...", "text": "..." }
}
```

- 原始文本原样放字符串，不二次解析、不美化，避免导出过程本身改字节。
- 文件名 `exdark_store_backup_<yyyyMMdd_HHmmss>.json`，MIME `application/json`；继续走 `AndroidBridge.exportDoc`，不要用 `exportCsv`（Java 侧 MIME 写死）。
- 导出成功置内存标记 `bootExported=true`。**只有**这个标记为真，`导入新计划` / `新建空白档案` 才可点。
- 导出失败（无桥/权限/写失败）：保持禁用；给 `我已通过其他方式备份，继续` 的二次确认入口（默认关闭，红色提示），记 `bootOverride=true`。这是显式同意，不是静默放行。

## C5. 恢复路径

### C5.1 导入新计划

- 走现有计划导入解析，但目标状态从零构建，不读旧账本的任何键。
- 只接受 `RPL-Plan-v3` 及契约 `accepted` 里的版本；旧 Gear 字段在 `xValidateGear` 被拒。
- 成功后：新 `state` + `gearProfile={v:1,byVenue:{},fallback:{}}`；`READONLY=false`；`save(true)`。
- 失败：留在阻断页，显示具体错误行，不写盘。

### C5.2 新建空白档案

- 语义 = 全新安装：`schemaVer=9`，`profile`/`structure`/`weeks`/`gpp` 来自 `SEED`，空账本，空 profile。
- 二次确认文案必须写明「旧训练记录不会恢复；旧档已导出到 …」。
- 写盘前再次检查 `bootExported || bootOverride`；否则拒绝。
- 成功后 `READONLY=false`，重建界面。

### C5.3 不得发生的三件事

1. 阻断态下 `flushSave()` 已拦；但 `savePrefsOnly()` 目前**不拦**。本版必须加 `if(!state||READONLY) return;`，否则任何偏好写入都可能覆盖 prefs 分片。
2. 不许在阻断页调用 `ensureShape()` / `migrateStateV8()` / `xPlanDictToState()` 的“补默认”路径。
3. 不许把旧分片先 `delete` 再尝试解析；解析失败也必须保留原文并可导出。
